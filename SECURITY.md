# Security policy

## Reporting a vulnerability

Please report privately through GitHub: on the repository's **Security** tab choose **Report a vulnerability**, or go to <https://github.com/joffrey-b/solanum/security/advisories/new>. Please do not open a public issue for a vulnerability.

Say what you did, what happened, and which version you ran (the About panel shows it). A small proof of concept helps. Solanum is maintained by one person and has no bug bounty, so a reply can take a while; you will get one.

## Supported versions

Only the latest release receives security fixes.

## What Solanum is designed to protect

- **Your vault at rest.** Saved servers, logins, keys, commands and notes are in one file sealed with Argon2id and AES-256-GCM. Someone who gets the file, while the profile is locked, has to guess your master password, at the cost of a full Argon2id run per guess.
- **Your connections.** Host keys are pinned on first use, and a changed key gets a red warning. SHA-1 algorithms are refused unless you allow them for a server.
- **Your computer against a hostile server.** What a server sends is treated as untrusted: file names cannot escape the folder you download to, programs are never opened from it, opening a file or starting a local shell asks in a system dialog the window's page cannot answer for, and on Linux the page that draws terminal output runs in WebKit's sandbox where the system allows it.
- **Your privacy.** No account, no cloud, no telemetry. The only connection beyond your own servers is the update check described in the README. Installing on Windows can make one more, to Microsoft, when WebView2 is missing (see Known limitations).

## What it does not protect against

- **Malware running as your user, or anyone using your unlocked session.** While a profile is unlocked its key and contents are in memory, and a program with your privileges can read them, log your keys or watch your screen.
- **A weak master password.** Argon2id slows guessing down; it cannot make a guessable password safe.
- **A compromised window.** A script running inside the app's page could use what the app's screens can do while a profile is unlocked. See [Known limitations](#known-limitations) below for exactly what that covers.
- **The first connection to a server.** Trust on first use means the key seen first is the key pinned. Compare the fingerprint when it matters.
- **The servers you log in to.** A server sees what you do on it. Solanum limits what a server can do to your computer, not what it can do to the data you send it.
- **Tampered downloads.** Windows and macOS builds are not code-signed. Each release has a `SHA256SUMS` file and a build-provenance attestation, described in the README under "Verifying a download".

## How the vault works

1. **Your master password becomes a vault key — on your device.** When you unlock, your password is run through Argon2id to derive a key. The backend's copy of the password is zeroized the moment derivation finishes, and it is never stored or sent anywhere. (The webview's own copy of what you typed can't be wiped from JavaScript memory — lock the app when you step away.)
2. **Profiles are sealed with AES-256-GCM — on your device.** Every saved server (credentials, keys, tunnels, notes, mirrors) is compressed and encrypted with that key. What hits disk is opaque ciphertext. The file's header, including its Argon2id settings, is authenticated too: changing any byte makes the file refuse to open, settings outside sane limits are rejected before any key derivation runs, and a file asking for more memory than the device can give is refused when that memory cannot be reserved (a device short of RAM may still close the app).
3. **The vault is one encrypted file** (plus `<name>.solanum.bak`, the file as it was at the last unlock, just as encrypted) under your OS app-data directory. If your machine is compromised while Solanum is locked, an attacker gets ciphertext, and cracking it costs a full Argon2id run per password guess — so use a long passphrase.

## Defences in detail

- Master key kept in zeroized memory, wiped on lock and on quit. When the window's page starts again (a reload, or after the web view crashed) it locks the profile first: every connection, tunnel, mirror and transfer is stopped, so the profile picker does not hide a session still running
- Vault files (and the folder they live in) are readable by your user only, on Linux and macOS
- TOFU host keys with per-connection nonce binding (resists prompt-race attacks). A changed key, or a known host suddenly presenting a key of another type, gets a red warning that lists the key you trusted; Solanum asks first for the key types you already trust, as OpenSSH does. The fingerprint prompt waits up to 90 seconds for you without the connection timing out underneath it, and a refused or unanswered prompt stops auto-reconnect instead of coming back every few seconds. If the saved host keys cannot be read, the connection is refused rather than treated as a new host
- **Old algorithms are off unless you allow them for a server.** SHA-1 key exchange (`diffie-hellman-group1-sha1`, `diffie-hellman-group14-sha1`), HMAC-SHA1 and `ssh-rsa` (SHA-1) signatures, for host keys and for RSA login keys, are refused unless "Allow legacy algorithms" is on in that server's settings; even then they are offered last, and the connection log says when one is used. Key exchange goes by Solanum's own order, whatever the server lists first: curve25519, then ECDH on the NIST curves, then the rest, so a server offering ECDH never gets SHA-1. Compression is only ever negotiated after login
- **A misbehaving server cannot hang a connection.** Every step of connecting waits a bounded time (the questions you are asked have their own, longer limits), keyboard-interactive login stops after 8 rounds, and a server that does not answer a request for a terminal, a file browser or a command holds the rest of the session for 15 seconds at most. Logins that need two steps (a key and then a password or a code) work; for a key and a password, type the password when the connection asks for it (a password saved for a password login is never sent instead of a key). Keyboard-interactive questions name the server asking, show its text apart from Solanum's own, and keep answers to anything that looks like a password masked
- **Auto-reconnect backs off, and says why.** After a dropped connection it waits 5 seconds, then longer between attempts, up to a minute, and stops for good on a refused login or host key. The banner and the Activity log give the reason: what the server said, or that it stopped answering. When Solanum itself closes a connection or terminal to reconnect, the Activity log says that too
- **A session the server ends stays ended.** When a shell exits (`exit`, an idle logout, a reboot) and it was the session's last terminal, Solanum closes the connection too, so nothing stays logged in on the server however long the tab stays open. The same goes when the server says goodbye, or closes a direct connection itself, as a Cisco switch does after `exit`. Nothing reconnects by itself then: R in the terminal, or Reconnect, logs in again from the start (your key, or the password question again if you typed it) and keeps the scrollback. A connection the network loses still reconnects by itself. With several terminal tabs, the connection stays until the last one ends; their tunnels, file browser and mirrors end with the session
- Strict Content Security Policy, and a webview permission set cut down to exactly what the UI calls: no shell, filesystem, opener or general-purpose core plugins are exposed to it, and of the app's own commands only those its screens use
- **Opening a file asks first, in a system dialog.** Before a file is opened on your computer (a remote file you live-edit, or a file in the local pane, which may have come from a server), the app itself, not the window's page, shows a system dialog naming the file, with Cancel as the default button (on Linux and Windows, Open only becomes clickable after a moment, so keys you were typing cannot press it). Never opened: programs, installers, shortcuts and disk images (`.exe`, `.msi`, `.lnk`, `.app`, `.pkg`, `.dmg`, `.desktop`, `.AppImage` and the like), executable files that have no extension or start like a program, and on Linux files whose content is a launcher or a Windows program whatever their name. For a local file Solanum offers to show it in its folder instead; a remote one can still be downloaded. Scripts Windows would run (`.bat`, `.ps1`, `.js`, `.py` and the like) open as plain text in Notepad, and `.py` files on macOS in your text editor
- **Local shell tabs** start your login shell or one from your system's list (`/etc/shells`; on Windows PowerShell, PowerShell 7, Command Prompt, WSL or Git Bash), never a program the window names, and each start asks in a system dialog first
- **Downloads stay in the folder you chose.** A server picks the names it lists, so each name is checked before it becomes a local file: names with path steps, characters your system treats specially (on Windows also `\ : * ? " < > |`, device names such as `CON`, trailing dots or spaces) or hidden direction-changing and zero-width characters are refused (rename the file on the server to download it), and a folder download skips such entries and says how many. A downloaded name starting with a dot is never saved directly in your home folder, where it would be a configuration file. The file browser's lists, dialogs and messages show names with those hidden characters spelled out (fields you edit keep the real name)
- **The file browser stays out of sensitive places.** It does not write, rename or delete in system folders, auto-start locations, `~/.ssh`, `~/.gnupg`, shell start-up files and similar, does not replace or remove the folders that hold them (such as `~/.config`), and does not delete your home folder; reading system files to upload them is fine
- Deleting a remote folder deletes everything inside it; symbolic links inside are removed, never followed
- **The folder mirror stays out of them too.** Its local folder cannot be your home folder, a folder that contains it, or a protected folder (`~/.ssh`, system folders, auto-start folders); its server folder must be an absolute path below `/`. It never follows a symbolic link inside the folder, on either side. A server file it cannot check (no permission, a timeout) is listed in the preview and left alone
- **What you type stays where you typed it.** Command history keeps only a line typed key by key that appeared on screen as you typed it, so nothing typed at a password prompt (in any language, or one that shows `*` per key); each session's tab menu can turn it off, Settings > Maintenance clears it, and deleted data is overwritten in the vault rather than left in the file. Broadcast input pauses, with a banner, while the terminal you type in is asking for a password, and the terminal's own answers to a program's queries are never sent to the other sessions. Snippets expand only on such a typed line and never press Enter for you. A link a program prints opens in your browser only after you have seen its real address (http and https only)
- **Session logs** ("Always save terminal output to file") are created readable by your user only on Linux and macOS, and never overwrite an existing file; a log that cannot be started (for example in a folder Solanum does not write to) is reported in that terminal, which runs without it. Release builds do not copy the connection log (hosts, ports, user names) to the console, which desktops often keep in the system journal
- **Live edit uploads only to the server a file came from.** If the session later reaches another server (its address was edited and the tab reconnected, or it presents another host key), saves are not uploaded and your copy is kept
- **WebKit sandbox on Linux.** The webview's renderer process handles whatever a server sends (terminal output, file names, logs), so on Linux it runs inside WebKit's bubblewrap sandbox whenever the system supports it (the `.deb`, `.rpm` and Arch packages on a normal desktop). Where it can't run, Solanum starts without it and prints a warning on stderr: inside an AppImage, or when `bwrap` is missing or user namespaces are blocked. If the window ever stays blank, start the app with `WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS=1` (and please report it); to force the sandbox on, set `WEBKIT_FORCE_SANDBOX=1`. The workarounds Solanum sets for its own window on Linux (software rendering, XWayland on a Wayland session) and the sandbox switch are removed from the environment of the programs it starts: local shells, and the files and links it opens

## Known limitations

These are unfinished or inherent, and kept up to date with the code.

- The window's page is trusted with what its screens can do. A script running inside it (which would take a bug in Solanum or a compromised frontend dependency) could use those features while a profile is unlocked: show saved passwords and private keys, run commands on connected servers and type into an open terminal or local shell, upload files the file browser can read, open tunnels (the question before one listens beyond loopback is the page's own), and read the clipboard while the window has the focus. Opening a file and starting a local shell need your answer in a system dialog.
- Input a server has not taken yet is held up to 1 MiB; beyond that, keys are not sent, with a notice, until the server has taken all of it. After a paste larger than that into a slow connection, keys typed before it is through (Ctrl+C included) are dropped, not sent late.
- Recognising a password prompt (to pause broadcast input there) is a guess from the prompt's text. A prompt it does not recognise gets your keys typed into the other broadcast sessions too.
- Logging in with an **RSA key** signs with the pure-Rust `rsa` crate, which has a timing side channel and no fixed release (RUSTSEC-2023-0071). It matters only to an attacker who can measure your machine's timing very precisely. Ed25519 and ECDSA keys are not affected, so prefer them where the server allows.
- The SSH library (`russh` 0.65) is built on release-candidate versions of the RustCrypto crates (`ssh-key` 0.7.0-rc, `rsa` 0.10.0-rc). russh pins them exactly and they will move to final releases when russh does.
- **Replacing a file on a server** goes through a temporary file and a rename. The new file gets the old one's permissions, owner and group, but not its hard links, ACLs, extended attributes or SELinux label; it is a new file, so a program holding the old one open keeps reading the old content; and with OpenSSH (whose plain SFTP rename will not replace a file) the name is missing for a moment while the old file is moved aside. Solanum writes into the file in place instead, as most clients do, when the owner or group cannot be kept, the folder is not writable, the server does not report the file's owner and permissions, the name is a link to something other than a regular file, or the file cannot be renamed (a single-file mount); a failure there can leave it partly written. A read-only file is never replaced around its mode. A connection lost during an upload can leave a hidden `.<name>.<random>.solanum-part` (or `.solanum-old`) file on the server.
- **The folder mirror** writes through the same temporary file, except for a file the server only lets Solanum rewrite in place (one owned by someone else, or in a folder you cannot write): Stop lets that upload finish, but a connection lost in the middle leaves it partial. Its soft delete keeps the server versions the first sync replaces in `.solanum-trash` too (if the trash cannot take one, it stays beside the file as a hidden `.<name>.<hex>.solanum-old`; a file rewritten in place cannot be kept), and the trash is never emptied automatically. Its mass-delete pause counts deletions as the system reports them: a folder deleted or moved out of the mirror in one go counts as one, and everything in it then goes to the trash (or is removed, with soft delete off). Edits made while the first sync runs can be lost: save and close editors before you start it.
- **Dynamic tunnels** (the SOCKS and HTTP proxy) have no password, like `ssh -D`: any program on this computer can use one, and so can any machine that reaches it when it listens beyond loopback. On the server, an address other than loopback for a remote tunnel takes effect only where sshd allows it (`GatewayPorts clientspecified`); with `GatewayPorts yes` every remote tunnel listens on all of the server's interfaces, whatever is asked.
- A live connection is checked every 30 seconds by asking the server for a keepalive reply (what OpenSSH's `ServerAliveInterval` does). A server that never answers such requests would be taken as gone after about 20 seconds of checking; OpenSSH, Dropbear and the common SSH libraries answer them.
- **Live edit** keeps syncing until you stop it in the file browser's "Live edits" list (a save still pending is uploaded first), disconnect, lock the profile or quit. If a change could not be uploaded by then, the local copy is kept and Solanum says where it is. If Solanum crashed or was killed, its next start removes the copies that match the server and lists the ones it keeps.
- **Docker live logs** end on the server when you stop them, disconnect or lock: Solanum asks the server to end `docker logs` (an SSH `signal` request, which OpenSSH honours). A server that ignores such requests leaves the `docker logs -f` of an idle container running until it prints its next line.
- **On Android** Solanum keeps sessions open in the background with a foreground service, but Android can still end a background app when memory runs short, and some phone makers' battery savers stop background apps regardless. If sessions drop while Solanum is in the background, exempt it from battery optimisation in the system settings. Android 13 and later also let you stop it from the notification shade's list of active apps, which ends its sessions.
- **The Windows installers and WebView2.** On Windows, Solanum's window is drawn by Microsoft's WebView2 runtime. Windows 11 includes it; some Windows 10 installs do not. When the installer finds no WebView2 in the registry, both the `.exe` and the `.msi` download Microsoft's WebView2 bootstrapper from `https://go.microsoft.com/fwlink/p/?LinkId=2124703` and run it, and the bootstrapper downloads and installs the runtime from Microsoft; without a network connection the installation stops with an error. This happens only while installing and only when WebView2 is missing: Solanum itself never makes this connection. WebView2 is a Microsoft component, which Microsoft keeps up to date as on any Windows machine. To avoid the download, install the runtime first with Microsoft's offline "Evergreen Standalone Installer"; the Solanum installer then finds it and downloads nothing.
- **How the Linux packages are built.** The AppImage is assembled with tools the Tauri bundler downloads while building (linuxdeploy and its plugins), without checking their hashes, and the Arch package is built in the current Arch Linux image. The `.deb` and `.rpm` packages and the Windows, macOS and Android builds do not use either.
- Quitting waits at most 5 seconds for everything to stop (the vault is saved first). A Solanum that is killed or crashes stops nothing; its connections end with the process, and its next start cleans the live-edit folder it left.
- **Not everything is in the vault.** Session logs, if you turn them on, are plain text in the folder you chose. The window's own storage, outside the vault, keeps per-profile folder paths, bookmarks and layout choices in plain text; passwords and keys never go there.
- A host key is checked when a connection is made. The SSH library does not check it again when the connection re-keys (every hour or 1 GB). That happens inside the already authenticated, encrypted connection, so only the server you are connected to could switch keys there; OpenSSH does check.
- The dependency audit (`cargo audit`, `npm audit`) runs weekly in CI; see `.github/workflows/audit.yml`. It fails on a new vulnerability or a crate newly found unsound or yanked, and lists unmaintained crates without failing. What it reports today, each named in the audit so it does not fail: the `rsa` vulnerability above, and `glib` 0.18's unsound iterator, fixed only in releases the GTK 3 stack does not use. The unmaintained crates are inside the Tauri/GTK stack (`unic-*`, `proc-macro-error`, `zbus_names`, `zvariant`, `pin-utils`), which Solanum cannot replace by itself.
